# KSR-MoE 实测报告（2026-10-23）

需求原话：**全新架构的大模型，知识库和专家解耦，由路由根据需求调用对应专家到显存计算，
专家调用内存里面的知识库，还由自我迭代功能，显存常驻一个常识专家，用于修正和常识答复。**

这份报告只写两件事：**测到了什么**，和**没测到什么**。所有规格数字来自
`tools/ksr_calc.py`（唯一数字来源，`--selfcheck` 必须通过），不由本文手工计算。

---

## 1. 架构（已实现，可运行）

| 组件 | 实现 | 位置 |
|---|---|---|
| 路由 | 每层独立路由，输出 专家 id / 权重 / 置信度 / need_knowledge + 负载均衡辅助损失 | `ksr/nets.py::Router` |
| 常识专家（常驻） | 每层始终激活的共享 FFN；同时是低置信时的独立兜底应答路径 | `KSRBlock.forward` 第 327-328 行 |
| 技能专家 | 每层低秩旁路适配器**成栈**（整栈原子加载），热集 LRU | `SkillExpertPool` |
| 知识库 | SSD+内存，jsonl + 向量侧车文件，检索有**三重硬预算** | `ksr/knowledge.py` |
| 三档策略 | L0 高置信直答 / L1 中置信校验 / L2 低置信走常识专家兜底并强制检索 | `ksr/selfevolve.py::route_policy` |
| 自我迭代 | L1 记忆（回写→检索命中）、L2 参数（只解冻单个专家的适配器 + 防遗忘检查） | `ksr/selfevolve.py` |
| 知识库策展 | 常识专家判定 新增/合并/否决 + 冲突标记，三条硬约束写死在代码里 | `ksr/curator.py` |

混合注意力：只有 `4k+1` 层做全注意力，其余 Gated DeltaNet（状态恒定）——这是显存和算力
节省的最大来源。

## 2. 规格数字（解析计算，7B 定稿 `tools/configs/ksr7b_32L.json`）

| 配置 | 总参 | 每 token 激活 | decode FLOPs | 占稠密 7B | 常驻显存 |
|---|---|---|---|---|---|
| 原稿 v1 | 39.96B | 6.97B | — | 86% | 81.5GB |
| **KSR-7B 定稿（32 层全 MHA）** | **6.84B** | **3.77B** | **11.9 GFLOPs** | **38%** | **14.29GB** |
| KSR-7B 紧凑版（24 层 GQA） | 4.27B | 1.95B | 7.2 GFLOPs | 23% | 6.43GB |
| 稠密 7B 基线 | 7.01B | 7.01B | 31.2 GFLOPs | 100% | 31.2GB |

诚实说明：24 层 GQA 那一档叫"7B"是不诚实的（同底座稠密只有 4.69B）。**"7B"这个标签
本身没有意义，有意义的表述是"每 token 算力为稠密 7B 的 X%、常驻 Y GB"。**
32 层定稿是为了让"7B"这个参数量标签站得住（注意力参数与标准 7B 完全相同 2.15B），
代价是 38% vs 23%、14.29GB vs 6.43GB。全部是配置驱动，换回来只改一个文件。

## 3. 原型实测（`python -m ksr.experiment`）

原型 `ksr_tiny_scaled`：2 层、h=256、16 个专家（秩 128）、常识专家宽 64、词表 988、
4.29M 参数 / 每 token 激活 1.15M。任务：16 个领域 × 10 个意图（每领域一套互不相干的
答案词表），训练用两种句式，**评测用训练里没出现过的第三种句式**；另有 64 条端口→服务
事实，40 个端口训练、**24 个留出**，答案只存在于知识库、不在权重里。

### 3.1 知识外置 —— 成立（本报告最硬的结论）

| 条件 | 留出端口准确率 |
|---|---|
| 检索开 | **67%** |
| 检索关 | **4%** |

检索本身命中率 **100%**，平均注入 28.0 token/题（预算 96 之内）。三次独立运行分别是
46%、54%、67%，对照组始终是 0-4%。**答案确实不在权重里，加进上下文就能答对**——
这就是"知识库和专家解耦"要的效果，它被复现了三次。

### 3.2 路由分工 —— 未测出，且已定位原因

| 测量 | 结果 |
|---|---|
| 自然路由 | 31% |
| 固定只用专家 0（等价于没有路由） | 31% |
| 故意强制错误专家 | 31% |
| 路由置信度 | **0.062 ≈ 1/16（均匀）** |
| 三档策略分布 | 32/32 全部落到 L2 兜底档 |

强制任何专家都不改变答案，因为**专家输出要乘上路由给的权重**，而路由是均匀的——
均匀的路由等于把专家乘上 0.06，几乎归零。答案全部来自共享通路。

这不是"架构失败"，是一个明确的、可修的机制缺口，而且它正是设计阶段预测的那个：
交叉熵降到 0.02 之后，**负载均衡辅助损失反而主导梯度，把路由按回均匀**。
训练里 aux 确实偏离过 1.0（0.87、0.91），但那种偏离没有转移到留出句式上。

### 3.3 自动纠错 —— 未测出
校验器准确率 0.59（三分类，随机是 0.33，但远不够用），纠错前后都是 31%。
它没有能力可靠地判出"这次是错的"，所以既救不回也懒得改。

### 3.4 自我迭代 L1（记忆级）—— 不通
纠正写回并审核通过之后，检索 100% 能捞到那条新条目，但模型仍答 `svc19`（应为 `svc16`），
复犯率 1→1。卡点不是检索，是模型从上下文抄写的正确率只有 67%。

### 3.5 自我迭代 L2（参数级）—— 机制通了，效果不稳
只解冻一个专家的适配器（196,608 参数），loss 8.95→2.25，
防遗忘检查 67%→67%（**没被带坏，这是"专家解耦"唯一被直接测到的好处**）。
但答案没变（`svc19`→`svc19`）：单样本 80 步不足以压过原有分布。
上一轮（4 专家配置）同一段代码曾成功把错答改成正确答，所以它是**不稳定**，不是不能。

### 3.6 高效 / 低硬件 —— 这个尺度测不出来
同底座、同参数量的稠密基线（FFN=2288，4.29M）23,262 tok/s，KSR 原型 4,862 tok/s，
**0.21×**。2-4M 参数时，路由和各模块的调用开销远大于 FLOP 节省。
**效率主张只能用第 2 节的解析 FLOPs/显存说话，不能用原型的墙钟时间冒充。**

## 4. 这一轮真实修掉的 bug（每一个都曾产生过误导性的数字）

1. `MoEGate` 先 top-k 再 softmax，k=1 时恒等于 1 → 门控梯度为零。
2. 绑定嵌入用默认初始化 → 初始 loss 244（应为 ln V≈6.0）。修：std=0.02 + 输入 ×√h。
3. `encode()` 逐字符编码 → 词表里的多字符条目**永远编不出来**，答案被拆成 5-7 个字符，
   而生成只给 `max_new=4` → **准确率被钉死在 8%**（正好是短答案的比例）。
4. 训练序列前面加了前缀 token、推理没加 → RoPE 位置整体错一格 → 训练 loss 0.014、评测 8%。
5. 混合检索的词面信号加在了**已截断的 top-k** 上 → 加了等于没加。改成先多召回再重排：
   **检索命中率 17% → 100%**。
6. `force_expert` 只在"路由恰好选中同一个 id"的位置生效 → 所谓"选错专家"其实是
   "完全不用专家"；L2 微调因专家压根没进计算图而报 `does not require grad`。
7. 知识库目录没在每轮开始前清理 → 条目数翻倍（64 变 128）。
8. 检查点只在训练全部结束后存 → 一次断电就把整个训练丢掉。改成每 100 步存 + 最后一步必存。

## 5. 由实测得出的设计约束（要写进 SPEC，不是调参技巧）

- **检索必须稀疏+稠密混合，且先多召回再重排。** 模板化问句共用句式，均值池化的嵌入
  几乎一样，纯向量只有 17%。
- **训练与推理必须共用同一条编码路径**（同一个前缀、同一个分词器行为）。否则位置错位，
  会出现"训练 loss 很低、评测接近随机"这种最难查的假象。
- **生成预算必须与分词器一致**：答案是单 token 还是多字符，直接决定 `max_new`。
- **路由必须有监督来源**（领域标签或 oracle 蒸馏）。只有 CE + 负载均衡时，CE 收敛后
  辅助损失主导梯度，路由塌回均匀——实测置信度 0.062 ≈ 1/16。
- **置信度阈值必须按分位数/温度校准。** 否则三档策略会全部落到兜底档（实测 32/32 走 L2）。
- **共享通路容量大于专家时，模型不需要分工。** 要检验解耦，常识专家必须窄到装不下全部
  领域（实测：把 reasoner 从 512 砍到 64，4 领域任务仍然全对——因为任务本身不需要容量）。
- **原型尺度测不出效率**，只能用解析 FLOPs/显存。

## 6. 下一步（按性价比排序）

1. **给路由加监督**：语料本来就有领域标签，加一路蒸馏损失即可（约 20 行）。这是让
   "专家解耦"变得可测的唯一前提。
2. **阈值改成校准值**：用留出集的分位数定 L0/L1/L2，而不是绝对值 0.35/0.85。
3. **L2 微调改成多样本 + 格式保持项**：单样本会把输出格式带崩（曾出现微调后输出空串）。
4. 校验器需要更强的信号（目前 0.59 不可用）。

## 7. 机器环境问题（与本项目无关，但影响实验）

一夜之间四次硬断电：`Kernel-Power 41` + `Event 6008`，无 `WER-1001` bugcheck。
后两次（02:31、02:46）**我的进程数为 0，是空载断电**，间隔 10-15 分钟一次。
`WHEA-Logger Id=2 corrected hardware error` 今天两条（02:04、02:32），7 月还有一整批。
`CrashDumpEnabled=3` 且 `volmgr 46: Crash dump initialization failed` → 转储写不出来，
所以每次断电都查不到原因。结论：这是硬件层（内存/供电/散热）在升级恶化，
不是负载或线程数造成的——2 线程时整机 18% 跑十几分钟没事，空载时也会断电。

## 8. 与"同参数量稠密模型"的实测对照（`tools/bench.py`）

口径：按**总参数量**对齐——硬件门槛由总参数量决定，这是唯一对稠密模型有利的公平口径。
两边跑同一份前向代码：稠密基线不是另写一个模型，而是把常识专家的宽度解到刚好等于目标
参数量（解出来 FFN=2617），并把 12 层全部设成全注意力——它就是标准稠密 transformer。
batch=1、fp32、CPU 8 线程、带缓存的增量解码。

| 尺度 | 总参数 | 每 token 激活 | 短上下文(128) | 上下文 1024 | 峰值驻留 |
|---|---|---|---|---|---|
| KSR-180M（3 层全注意力 + 9 层线性） | 183,076,652 | 114,917,676（62.8%） | 20.25 tok/s | 4.79 tok/s | 1.20 GB |
| 同参数稠密基线（12 层全注意力） | 183,352,620 | 183,352,620（100%） | 17.75 tok/s | 4.35 tok/s | 1.18 GB |
| **比值** | 1.00 | **0.63** | **1.14×** | **1.10×** | 1.02× |

**这一条必须写清楚，否则整个卖点会被误读**：激活参数少了 37%，CPU 上 decode 只快 10-14%。
原因是 batch=1 的解码由**内存带宽和调用开销**主导，不是 FLOP 主导——两边每个 token 都要读
完整的嵌入、常识专家和注意力权重，省下来的只有专家那一小块。峰值驻留几乎相同也是同一个
道理：**同总参数量下常驻权重的要求本来就相同，这个架构省的不是"模型大小"。**

所以"资源占用少多少 / 硬件门槛低多少"目前只有两处是解析结论、尚未实测：
（a）KV 与线性注意力状态——12 层里只有 3 层做全注意力，长上下文下这一项是 4 倍差别；
（b）int4 量化 + 冷专家不进显存。**要拿到能引用的实测倍数，必须在 GPU 上或大 batch 下测**，
那里才是 FLOP/带宽主导。CPU 单并发下 1.10× 就是诚实数字，不能拿 62.8% 去冒充 1.6×。

## 9. 带路由监督的训练（`work-sup`，`router_supervision_weight=0.5`）

加上"一个领域固定对应一个专家"的 oracle 蒸馏之后，同一份代码、同一个配置：

| 指标 | 无监督 | 有监督 |
|---|---|---|
| 知识外置（检索开 / 检索关） | 67% / 4% | **83% / 0%** |
| 路由置信度 | 0.062 ≈ 1/16（均匀） | 越过 L1 阈值：13 题走 L0、19 题走 L1，不再全部兜底 |
| 领域→专家分配 | 互相挤占（4 个专家被 16 个领域抢） | 基本 1 领域 1 专家（windows→0, linux→1, physics→3, chemistry→4…） |
| L1 记忆级自我迭代 | 复犯率 1→1 ✗ | **复犯率 0→0 ✓**（纠正后答对） |
| 自然路由 vs 固定只用一个专家 | 31% / 31% | 59% / 59%（**仍然没有差距**） |

监督把路由从"均匀"救成了"分工"，知识外置和自我迭代都因此变好了。但"路由比只用一个专家强"
在这个尺度上仍然测不出来：4.3M 参数时，单个专家加共享通路已经记得住这些答案，
**任务本身没有超出单专家的容量**——要测出这个收益，任务规模必须超过单专家的容量。

## 10. 同日第二轮：知识归属、检索与呈现、动态 MoE 的实测边界

规则与基准的完整定义在 [KNOWLEDGE.md](KNOWLEDGE.md)；本节只记数字和被更新掉的结论。

### 10.1 本报告里被更新掉的数字（以本节为准）

| 位置 | 原文 | 现为 | 原因 |
|---|---|---|---|
| 3.1 知识外置 | 检索开 75% / 检索关 8% | **92% / 4%** | 冲突改写训练 `KSR_CONFLICT=0.5`：模型学会"【已知】写什么就答什么" |
| 主张6 新事实 | 59% = 手抄上界 | **89% = 手抄上界** | 同上；证据优先率 73% → **91%** |
| 8 效率 | "必须在 GPU 上或大 batch 下测" | **该说法被证伪**：batch 越大比值越差 | 真因是实现（分发开销随候选数增长），不是尺度 |

### 10.2 三个存储位置的清零消融（本轮最硬的结论，方向是负的）

同一种探针（推理期把该组件输出清零）测两个配置的 checkpoint：

| 清零的组件 | `ksr_tiny_scaled` | `ksr_tiny` |
|---|---|---|
| 全部开 | 56.2% | 56.2% |
| **技能专家（全部）** | **56.2%（0 题变化）** | **56.2%（0 题变化）** |
| 常识 FFN | 43.8% | 3.1% |
| 两个 FFN 都关，只剩 embedding + 注意力 | 43.8% | 0.0% |

两个配置合起来：知识要么在 embedding + 注意力里，要么在常识 FFN 里——**都在必须常驻的部分，
都不在技能专家里**。把任务加难也换不来结论：每领域映射数 40、步数按映射数同步放大、
答案集合固定（词表 989 不变）、留出集放大到 128 题之后，开专家 39.1% / 清零 41.4%，
**gap = −2.3pp ± 8.7pp**，与 0 无法区分。此前 32 题上的 +9pp、+6pp 是噪声。

所以"路由精准激活专家"要成立需要两个条件同时满足：知识必须是**算出来而不是查出来**的、
专家要多到**装不进显存**。当前两个都不满足——这是尺度与任务的问题，不是调参问题。

### 10.3 动态 MoE 的实测边界

- **分发实现重写**（分段 GEMM，整层只做一次 host 同步）：180M 上 fp32 b1 23.2→**27.2** tok/s、
  fp16 b8 113→**176**、b16 184→**317**；候选数扫描 E=1→16 的衰减从 **2.0× 降到 1.37×**
  （每 token 激活参数恒为 114.9M）。`--verify` 全程 `batch1_matches_generate: true`。
  去掉 MoE 只留混合注意力是 224/461，稠密基线 219/455 —— **原来那 2.0–2.5× 的差距全是实现**。
- **动态驻留**：省 28% 显存、赔 **12× 吞吐**（每步搬 62 次 × 18.9 MB 走 PCIe）。真实流量下
  容量 4 只罩住 54% 的选择；按领域看是集中的（`linux→专家1 76%`、`container→专家7 69%`）
  → 单领域部署成立、混流不成立。设计要求：**按流量预置、只换入不换出**。
- **动态数量**：没有可用信号——路由置信度 p25–p99 **全是 1.000**（oracle 蒸馏把靶做简单了）。
  要靠训练期信号解决，不是推理期阈值。
- **7B 测不了**：物理内存 16 GB，6.84B 参数 fp32 初始化要 27 GB。

### 10.4 检索与呈现（本轮修完，数字从此不动）

自适应候选池（随库规模放大，上限 4096）+ 符号倒排 + **两级排序**（先按符号命中数、再按混合分）；
呈现契约统一成一个 `render_context`，只有 rank-1 片段带 `【已知】`，只注入 1 段。
结果：2000 条库、池子压到 32 时召回 **286/286**（修前 5/286）；插入 200 条后旧题 **71%→71%**。

### 10.5 本轮修掉的 bug（每一个都曾产生过误导性的数字）

1. 符号匹配与余弦同尺度打分 → 近似向量并列时退化成插入序 → 2000 条库召回 5/286。
2. `best: Dict[...] = []`（给字典赋了列表）。
3. `ExpertStore._update_accounting` 把 `num_layers` 重复计入 → 180M 报 1.81 GB，真值 151 MB。
4. `enable_paging` 只设初始热集、没设容量 → 峰值显存不变、`loads_per_step=0`（全在 warmup 里搬完）。
5. 分页在 GEMM 循环**之前**一次做完 → 后面的专家把前面的换出 → `mat2 is on cpu`。改成循环内就地换入。
6. GPU 版 python 被 `PYTHONPATH` 里的 CPU torch 抢先导入 → 所有指标字段为空（症状是"cuda 不可用"）。
7. `tools/attrib.py` 硬编码配置文件 → 加载 `size mismatch`。现在把 `cfg_path` 存进 `model.pt` 自动解析。
8. 32 题留出集上的 +9pp / +6pp 是噪声。现在扩任务时留出集同步放大（每 5 条留 1 条），
   gap 必须带 95% 置信区间一起报。

### 10.6 下一步（按能不能产生证据排序）
